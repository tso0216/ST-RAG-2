# 03: 景點階層與退讓

**What to build:** 讓系統認得同一個景點的不同名稱，以及景點之間的包含關係。

階層檔：

- 定一份放在 repo 資料區、受版本控制的階層檔格式。每個節點記錄正式名稱、別名和母節點；節點可以是景點，也可以是區域，例如「淺草」「押上」。
- 起草現有 `place` 表的階層，交給研究者審稿。第一版只做別名合併和一層母子關係，不用座標。

系統行為：

- 計畫裡的地點名稱先比對別名，比對不到再用名稱 embedding 找最近的節點。
- 問母景點時，一律把子景點的片段納進來。
- 一筆都沒過門檻時，`space` 往上退一層，改查母節點。
- 還是沒有，就回傳空結果，並附上最接近的時段資訊。時間門檻不放寬。
- 生成時揭露退讓，沒有證據時明說沒有。

## Comments

### 實作摘要（implementer）

- **階層檔**：`data/place_hierarchy.toml`，TOML、每個節點一個 `[[node]]`，欄位 `name`（正式名稱）、`kind`（`景點`／`區域`，預設景點）、`parent`（母節點正式名稱）、`aliases`。格式和規則寫在檔頭。比對時不分全半形、大小寫，忽略空白。載入時檢查重複名稱、找不到的母節點、循環和不認得的欄位。
- **跟 `place` 表的對應**：載入時處理，不改 DB。階層檔沒收的 `place` 名稱自動當成獨立節點；只差空白或大小寫的寫法會併進對應節點。所以重建 DB 或重抽後，人工成果都還在階層檔裡。`python -m strag_v3.rag.hierarchy --db <DB>` 會印出階層樹，並列出還沒收進階層檔的 `place` 名稱。現有 41 個名稱全部有收。
- **名稱解析**：先比別名；比不到時，拿名稱 embedding 跟所有節點的正式名稱和別名比，取最像的。cosine 低於 `Params.place_min_sim`（預設 0.6）就當作階層裡沒有這個地點，回傳空結果。
- **退讓**：只退一層。母節點的範圍包含它所有的子孫節點，時間門檻不放寬。
- **空結果**：`SubQueryResult.nearest` 會附上查過的範圍裡，離問的時間最近的 3 個時段（只有景點、時間標籤和筆數）。時間距離是三個維度各自正規化後相加：月份週期距離 ÷ 6、小時週期距離 ÷ 12、平日／假日不符算 1。
- **用真實 DB 副本驗證**：問「一月平日去晴空塔的天望甲板」時，因為天望甲板沒有片段，退讓到東京晴空塔，答案開頭就說明了這件事。問「八月去雷門人會很多嗎？」時，答案說沒有八月的經驗，並列出最接近的時段：雷門、淺草寺、仲見世通，各 1 筆 1 月假日 13 點。

### 需要研究者審稿或決定

1. **階層草稿**（`data/place_hierarchy.toml`），以下是我自己判斷的地方：
   - `東京晴空塔城`（園區）→ `東京晴空塔` → `東京晴空塔天望甲板`，園區掛在 `押上` 底下。所以問「晴空塔」不會取到片段 12（晴空塔城六樓餐廳），問「晴空塔城」或「押上」才會。
   - `仲見世通`、`雷門` 掛在 `淺草寺` 底下（不是直接掛 `淺草`）；`伏見稻荷大社` 底下的表參道、千本鳥居、奧社奉拜所、四ツ辻同理。
   - 京都的區域節點是自己切的：`東山`（清水寺、三年坂與二年坂、八坂塔、高台寺、祇園）、`哲學之道一帶`（正式名稱是我取的，`哲學之道、南禪寺周邊` 當別名；底下有哲學之道、南禪寺、永觀堂、銀閣寺）、`嵐山`。`祇園` 標成區域，掛在東山底下。`東福寺`、`金閣寺`、`龍安寺`、`京都御所`、`錦市場` 還沒歸到任何區域。`伏見稻荷大社` 沒有設區域母節點，所以它本身沒有證據時不會退讓。
   - 有些別名是常識補上的，例如 `東京天空樹`、`淺草觀音`、`禪林寺`、`慈照寺`、`鹿苑寺`、`法觀寺`、`產寧坂`、`渋谷`，請確認要不要留。`狐狸烏龍麵（伏見稻荷表參道）` 的實際店名還不知道。
2. **`place_min_sim = 0.6`** 是用 text-embedding-3-large 量幾個例子定的。真別名：東京天空樹 0.62、Tokyo Skytree 0.69。不相干：大阪城 0.53、新宿 0.54、上野公園 0.60。`東京鐵塔` 對到 `東京晴空塔` 有 0.75，比真別名還高，門檻擋不掉。這類情況只能靠補別名，再加上生成端說明證據來自哪個地點。要不要在 dev 題目上調整，請決定。
3. **「最接近的時段」的距離**：三個維度等權相加，所以「同月份、但時段差 7 小時」（0.58）會排在「時段相同、但差 3 個月」（0.5）後面。要不要調權重，請決定。
