# 13: 用 OSM 解析地點，取代手建景點階層

**What to build:** 把地點從手建的階層檔改成用 Nominatim 解析成 OSM 物件（見 spec 的模組 2、模組 4、「資料與 schema 變更」「檢索計畫的形狀」）。取代 03 的階層檔、別名比對和「退到母節點」。

地點解析：

- 輸入日文名稱、城市、景點或區域，輸出一個 OSM 物件，或「沒有這個地點」。抽取和規劃器共用。
- 先查「名稱＋城市＋種類 → OSM 物件」的快取表，查不到才打 Nominatim：`countrycodes=jp`、`accept-language=ja`，取第一筆。景點用 `layer=poi`；區域用 `layer=address`，而且只接受行政區類型。
- 用公開伺服器，限每秒 1 次請求、帶自訂 User-Agent，原始回應存進 `main.db`，重跑時只讀快取。
- 景點存座標，區域另存範圍；每個地點記錄外圍行政區（從 `addressdetails` 取得）。

資料：

- `place` 表改成一列一個 OSM 物件（欄位見 spec）。`content` 表拿掉 `(poi_id, poi_name)` 的複合外鍵，`poi_name` 保留抽取時的原始名稱。
- 抽取 prompt 加上精簡的地點規則：寫到景點層級，局部寫成所在的景點，局部名稱留在 `content`；另外輸出日文名稱、`city`、景點或區域。mock 抽取時解析失敗就報錯，列出失敗的名稱。
- 重新抽取 `main.db`（會呼叫抽取用的 LLM 和 Nominatim，跑之前先跟研究者確認）。如果 12 的重新抽取還沒跑，兩張合併成一次。
- 刪除 `data/place_hierarchy.toml` 和手建階層的模組，以及只檢查階層檔的測試。

檢索、規劃、評估：

- 子查詢的 `space` 改成 `{name, name_ja, city, kind}`。問景點只取它本身的片段；問區域取區域本身和範圍裡所有地點的片段。
- 空間退讓改成退到外圍行政區；地點解析得到但沒有片段時也照常退讓。解析不到就回傳空結果。
- `group_by=place` 依地點分組，組名用繁中名稱，掛在區域本身的片段自成一組。
- 規劃器 prompt 加上跟抽取一樣精簡的地點規則。
- 規劃器正確率的 `space` 比對解析後的 OSM 物件和種類，不比名稱字串。
- 生成器揭露空間退讓時，講明證據來自哪個行政區。
- 現有 mock 題目檔的 `gold_plan` 改成新的 `space` 格式。
