# 01: 端到端最小版本

**What to build:** 研究者用一個命令輸入一句旅客問題，系統輸出答案、檢索計畫和取回的片段。這是第一條打通全程的路：

- Opus 規劃器以 zero-shot 產生只含一個子查詢的檢索計畫，子查詢有 `space`、`time`、`aspect` 三個欄位。prompt 只說明計畫格式，不放範例，也不提題型名稱。
- 時間標籤轉成時間分布（月 × 平日／假日 × 小時，共 576 格），這張先不做平滑。
- 計分是「語意分數 × (ε + 時空重疊度)」，用預設門檻篩選：時空重疊度用絕對門檻，語意分數用「不低於最高分減 δ」的相對門檻。
- 地點只做名稱完全相同的比對。
- 語意分數用 OpenAI `text-embedding-3-large` 計算，結果快取在 main.db。
- Opus 生成器依證據作答，並標明出處（不同文章就是不同旅客、不同天）。

不改抽取流程，現有 main.db 的片段直接能用。檢索計畫的結構和欄位的意思，請看 spec 的「檢索計畫的形狀」。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] 新的 `rag` 套件跟 `extract` 並列，提供一個命令：輸入問題，輸出答案、計畫和取回的片段（含時空重疊度和語意分數）
- [x] 時間分布轉換支援所有時間標籤格式：單一小時、小時範圍、單一月份、月份範圍（包含 `12-2` 這種跨年範圍）、季節（春 3–5、夏 6–8、秋 9–11、冬 12–2）、時段詞（`早上`、`中午`、`下午`、`晚上`、`全天`）用手訂梯形分布，`不明` 給均勻分布
- [x] 子查詢的 `space` 或 `time` 留空時，那個維度不限制
- [x] embedding 呼叫走同一個可替換的介面，測試時可以換成假的實作；API key 從環境變數 `OPENAI_API_KEY` 讀取；同樣的文字加同樣的模型不會重複呼叫 API
- [x] ε、門檻、δ、時段梯形邊界都是集中管理的可調參數
- [x] 第一批檢索 seam 測試用 pytest 撰寫，搭配記憶體內 SQLite 和假的 embedding，不打外部 API。至少涵蓋以下行為：
  - 問「傍晚」時，取回標成 `17`、`16-17` 的片段，擋掉標成 `早上` 的片段
  - `12-2` 和 `冬` 都能對上一月的片段
  - 欄位留空時，該維度不限制
- [x] 用現有 main.db 問「一月平日早上去晴空塔，看得到富士山嗎？要排多久？」，能取回 eval 裡對應的片段，並產生標明出處的答案
