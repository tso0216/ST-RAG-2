# 時空 RAG 主系統：週期性情境時間檢索

## Problem Statement

旅客想知道「某個景點在某個時間是什麼狀況」，例如「一月平日早上去晴空塔，看得到富士山嗎？要排多久？」。抽取流程已經把遊記拆成片段存進 DB，每個片段帶有景點、平日／假日、時段、月份。但現在沒有任何系統能用這些片段回答問題。

一般的 dense retrieval 只看語意，會把八月傍晚的經驗拿來回答一月早上的問題。硬性 metadata 過濾則太死：問「傍晚」時，標成 `17`、`16-17`、`晚上` 的片段都可能被漏掉；問「十二月」時，`冬` 也對不上。景點名稱也不一致：`晴空塔城` 和 `東京晴空塔城` 是同一個地方，天望甲板則屬於晴空塔，系統都無法辨認。

此外，研究者要把這套系統寫成國際論文，所以需要：

- 一個清楚的核心概念
- 一組可以重現的評估
- 能跟現有研究比較的 baseline 和消融實驗

現有的時間 RAG 研究（TempRALM、MRAG、DeFuzzRAG）處理的都是線性的文件時間。旅客問的卻是每年、每週、每天都會重複的「情境時間」，這個缺口目前沒有人做。

## Solution

做一套 RAG 主系統，核心是把旅客經驗的時間當成**週期性情境時間**，用分布來表示和比對：

- 片段和問題的時間標籤，都轉成「月 × 平日／假日 × 小時」週期格網上的分布，月份軸和小時軸頭尾相接、會平滑。檢索時用分布的重疊程度，乘上語意分數來排序，不做硬過濾。所以問十二月時，一月的片段也能被取回，但會排在後面，回答時也會說明「這是一月的經驗」。
- 系統先由 LLM 產生一份**檢索計畫**，計畫由一到多個子查詢組成，每個子查詢指定地點、時間、想知道的面向；不限制的欄位留空。題型不寫死，新的題型只是欄位的新組合。
- 景點用手建的**階層**做別名合併和母子包含：問母景點時一律納入子景點；完全沒有證據時往上退一層，回答時揭露。
- 附一套評估流程：擴充後的 mock 題目集，兩個 baseline，以及檢索、規劃、答案三方面的指標，用來驗證這個架構可不可行。

## User Stories

### 旅客（系統使用者）

1. As a 旅客, I want to 用口語問「某景點在某時間的狀況」, so that 我不用學任何查詢語法
2. As a 旅客, I want 系統優先採用跟我問的時間相符的經驗, so that 我拿到的資訊適用於我要去的那個時段
3. As a 旅客, I want 系統在沒有完全相符的經驗時，用相近時段的經驗回答並講明, so that 我知道這些資訊有多可靠
4. As a 旅客, I want 回答裡說明哪些內容來自不同旅客、不同天, so that 我不會把幾個人的經驗誤當成同一次
5. As a 旅客, I want 系統在完全沒有相關經驗時直接說沒有，並告訴我最接近的時段有哪些資料, so that 我不會被不相干時段的經驗誤導
6. As a 旅客, I want 問「什麼時候去人比較少」時，系統依時段整理各時段的狀況, so that 我能自己挑時間
7. As a 旅客, I want 問「傍晚在某區域哪裡適合看夕陽」時，系統依地點整理答案, so that 我能比較幾個候選地點
8. As a 旅客, I want 問「十二月傍晚跟晚上哪個比較不擠」時，系統分別找兩邊的證據再對照, so that 我拿到公平的比較
9. As a 旅客, I want 我說「晴空塔」時，系統也採用寫「天望甲板」「東京晴空塔」的經驗, so that 不會因為名稱不同而漏掉資訊
10. As a 旅客, I want 用「傍晚」「冬天」「週末」這種模糊說法提問, so that 我不用換算成精確的月份或鐘點
11. As a 旅客, I want 問題沒提到時間時，系統不限制時間, so that 所有相關經驗都會被考慮
12. As a 旅客, I want 時間寫得明確的經驗排在時間不明的經驗前面, so that 最可信的資訊先出現
13. As a 旅客, I want 跨年的條件（例如十二月到二月）正確處理, so that 冬天的問題不會漏掉一月和二月

### 研究者（論文作者）

14. As a 研究者, I want 用一個命令輸入問題就拿到答案、檢索計畫和取回的片段, so that 我能逐題檢查系統行為
15. As a 研究者, I want 時間標籤轉分布的規則是固定、可重現的程式, so that 論文結果可以被重現
16. As a 研究者, I want 時段詞的對應表（例如「早上」對應哪些小時、邊界多軟）明確寫出來, so that 論文能附上對照表並引用 Shwartz 2022 當依據
17. As a 研究者, I want 平滑頻寬是可調參數，設成 0 就等於不平滑, so that 我能做「週期平滑」的消融

19. As a 研究者, I want 用 eval 裡人工寫好的 `when` 直接當問題的時間（oracle 模式）, so that 我能把「問題解析錯誤」和「比對方法本身」的影響分開
20. As a 研究者, I want 規劃器只看計畫格式說明（zero-shot），不給範例和題型名稱, so that 我能主張系統有泛化性
21. As a 研究者, I want 能切換成 few-shot 規劃器, so that 我能量化範例的影響
22. As a 研究者, I want 每題有人工寫的 `gold_plan`，並另外量規劃器的正確率, so that 檢索變差時能分辨問題出在規劃還是比對
23. As a 研究者, I want 用 dense retrieval 和硬性 metadata 過濾當 baseline, so that 我能跟兩種常見做法比較
24. As a 研究者, I want 取回結果用集合的 recall、precision、F1 評估, so that 門檻式檢索取回的筆數不固定也能公平比較

26. As a 研究者, I want 由 LLM 評審逐條檢查答案是否涵蓋 `expect` 的重點, so that 我有答案品質的指標
27. As a 研究者, I want 量時間誤植率（答案把別的時段的經驗說成問題問的時段）, so that 我能證明揭露機制有效
28. As a 研究者, I want 題目分成 dev 和 test 兩組，門檻只在 dev 上決定, so that 不會在測試題上調參
29. As a 研究者, I want 依題型分組報告指標, so that 我能看出系統在哪類題目比較弱
30. As a 研究者, I want 一次跑完全部題目並輸出彙總結果, so that 我能快速比較各種設定和消融
31. As a 研究者, I want 延伸實驗可以改成讓 LLM 直接輸出時間分布, so that 我能跟固定規則的轉換比較
32. As a 研究者, I want embedding 有快取, so that 重跑評估不會重複付費也不會變慢
33. As a 研究者, I want 手建的景點階層放在版本控制的檔案裡, so that 重建 DB 或重抽文章時人工成果不會遺失
34. As a 研究者, I want 景點階層包含「淺草」「押上」這類區域節點, so that 「某區域附近」的問題也能對應
35. As a 研究者, I want 計畫裡的地點名稱比對名稱和別名，比對不到就當作沒有這個地點, so that 不會把不相干的地點硬對到某個節點上
36. As a 研究者, I want 現有的抽取流程和 `main.db` 的片段不用改就能用, so that 新系統不會打斷既有資料

38. As a 標註者, I want 遊記、題目、`gold_plan` 和景點階層由 agent 照 mock README 的流程起草，我負責審稿, so that 我省下寫作時間，但保有最後決定權

40. As a 標註者, I want 每個景點都有時空條件避開所有題目的負例遊記, so that 時間違規率有東西可量

## Implementation Decisions

### 名詞

- **片段**：DB `content` 表的一列，代表一則「某人在某時間到某地點」的經驗。
- **時間標籤**：片段或問題原本的字串，例如 `day_type`、`time`、`month`，格式跟抽取 schema 及 eval 的 `when` 相同。
- **時間分布**：時間標籤轉出來的分布，定義在「月（12）× 平日／假日（2）× 小時（24）」共 576 格的週期格網上。
- **時空重疊度**：問題和片段兩個時間分布的重疊程度，地點相符與否另外判斷。
- **檢索計畫**：由一到多個子查詢組成，外加 `group_by` 和 `compose`。
- **子查詢**：有 `space`、`time`、`aspect` 三個欄位，留空代表不限制。
- **退讓**：沒有證據時，往母景點找。
- **揭露**：回答時講明證據跟問題相符的程度。

### 模組

新開 `rag` 套件，跟 `extract` 並列。主要模組如下：

1. **時間分布轉換**（純函式、深模組）：輸入時間標籤，輸出 576 格的分布。
   - 單一小時、小時範圍、單一月份、月份範圍都支援，包含 `12-2` 這種跨年範圍。
   - 時段詞（`早上`、`中午`、`下午`、`晚上`、`全天`）用手訂的梯形分布，參考 Shwartz 2022 定邊界。
   - 季節定義：春 3–5、夏 6–8、秋 9–11、冬 12–2，三個月平均分配。
   - `不明` 給均勻分布。
   - 月份軸和小時軸套頭尾相接的平滑核，頻寬可調，設成 0 就不平滑；平日／假日這一維不平滑。
   - 不做太陽換算（日出、日落）和日曆換算（黃金週、盂蘭盆）。
2. **景點階層**：
   - 從版本控制的階層檔載入，對應到 `place` 表。檔案記錄每個節點的正式名稱、別名、母節點；節點包含景點和區域。
   - 第一版人工手建，只做別名合併和一層母子關係，不用座標。
   - 提供兩種功能：把名稱解析成節點（比對名稱和別名，比對不到就當作沒有）；查詢某節點的子孫與母節點。
3. **Embedding**：
   - 用 OpenAI `text-embedding-3-large`，透過雲端 API 呼叫，API key 從環境變數 `OPENAI_API_KEY` 讀取。
   - 結果快取在 `main.db` 的新表，以文字和模型為鍵。
   - 對外介面是「文字列表進、向量列表出」，測試時可以換成假的實作。
4. **檢索**（主要的深模組）：輸入一份檢索計畫，輸出分好組的證據。
   - 每個子查詢的處理：
     - 解析 `space`：對應到階層節點，並展開所有子孫節點；留空就不限地點。
     - 解析 `time`：轉成時間分布；留空就不限時間。
     - 用 `aspect`（沒有就用原問題）的 embedding 算語意分數。
   - 分數 = 語意分數 × (ε + 時空重疊度)。只要片段有任何一個時間維度是 `不明`，分數再乘上一個小於 1 的折扣。
   - 門檻：
     - 時空重疊度用寬鬆的絕對門檻，相鄰時段平滑後要能通過，例如問十二月時一月也能過。
     - 語意分數用相對門檻：不低於該子查詢的最高分減 δ。
     - 兩個都過才取，過門檻的全部取，不設上限、也不合併摘要。
   - 退讓：一筆都沒過門檻時，`space` 往上退一層到母節點再查一次。還是沒有，就回傳空結果，附上最接近的時段資訊。時間門檻不放寬。
   - 每筆證據附上片段內容、時間標籤、景點、來源文章、時空重疊度、語意分數、是否來自退讓。
   - 依 `group_by`（`month`、`day_type`、`time_of_day`、`place`，可以多選）分組排序，每個片段分到它分布質量最大的那一組。`compose` 是 `contrast` 時，各子查詢的結果分開交給生成端。
5. **規劃器**：用 Claude Opus 5.5，一次產生檢索計畫，以 structured output 輸出。
   - prompt 只說明計畫格式（每個欄位的意思和可用的值），不放範例，也不提題型名稱。
   - 可以切換成 few-shot，當對照實驗。
   - 不做反覆規劃，那是延伸實驗。
   - oracle 模式：用 eval 的 `when` 取代規劃器解析出來的時間。
6. **生成器**：用 Claude Opus 5.5，依分好組的證據作答。
   - 標明出處：來自不同文章的證據要說明是不同旅客、不同天。
   - 時空重疊度低或來自退讓的證據，要明講它跟問題的差距。
   - 沒有證據時，說沒有符合的經驗，並提供最接近時段的資訊。
7. **評估**：
   - 讀題目檔，跑系統，算出各項指標並依題型分組。
   - 檢索指標：取回集合對 `relevant_contents` 的 recall、precision、F1，以及時間違規率。
   - 規劃器正確率：跟 `gold_plan` 比對欄位，例如該留空的有沒有留空、`group_by` 對不對。
   - 答案指標：由 Claude Opus 5.5 評審算 `expect` 覆蓋率和時間誤植率。
   - 支援 dev 和 test 分組，以及切換 baseline、消融、oracle 模式。
8. **Baselines**：
   - dense retrieval：只用語意分數取 top-k。
   - 硬性 metadata 過濾：問題標籤和片段標籤必須字面相符，再依語意分數排序。

### 資料與 schema 變更

- 抽取 schema 和 prompt 不變。LLM 照舊輸出字串標籤，分布在查詢時即時計算，不存檔。
- `main.db` 新增 embedding 快取表。
- `place` 表跟景點階層檔的對應方式在實作時決定，可以新增欄位，也可以在載入時處理。人工成果以階層檔為準。
- 題目檔每題新增欄位：
  - `gold_plan`：人工寫的檢索計畫
  - `type`：停留、找時間、找地點、比較其中一種，只用於分組分析，系統不讀
  - `split`：`dev` 或 `test`
- 擴充後的 mock 照 mock README 的流程產生：約 10 個景點、30 題，其中 10 題 dev、20 題 test，每個景點都有負例。
- mock 階段維持繁中。真實 Reddit 資料和英文主實驗等可行性驗證通過後再做，不在這份 spec 範圍內。

### 檢索計畫的形狀

```
Plan:
  sub_queries: [SubQuery, ...]          # 一到多個
  group_by: [month | day_type | time_of_day | place]   # 可為空
  compose: merge | contrast
SubQuery:
  space: 地點或區域名稱 | null           # null = 不限
  time:  {month?, day_type?, time?}     # 跟 eval 的 when 同格式；省略的維度 = 不限
  aspect: 想知道的面向 | null
```

### 超參數

- ε、「不明」的折扣、平滑頻寬、時段梯形的邊界：先依常理定預設值，不在 test 題目上調。
- 時空門檻和語意門檻的 δ：在 dev 題目上決定。
- 論文另附敏感度分析。

## Testing Decisions

- **好的測試**只看外部行為：給定的輸入產生預期的輸出或排序，不檢查內部函式、中間值或實作細節。換掉內部實作時，測試不需要改。
- **Seam 1：檢索模組**，主要的測試點。
  - 輸入一份檢索計畫，輸出分好組的證據。
  - 測試時用記憶體內的 SQLite 塞入特定片段，embedding 換成假的固定實作，景點階層用小型測試資料，完全不打外部 API。
  - 時間分布轉換、平滑、計分、門檻、景點階層都在這個 seam 後面，不另外對它們寫單元測試。
  - 應涵蓋的行為：
    - 問十二月時，一月片段會被取回但排在十二月片段之後；平滑頻寬設成 0 時，一月片段取不回來
    - `12-2`、`冬` 都能對上一月的片段
    - 時間 `不明` 的片段排在時間明確且相符的片段之後
    - 問「傍晚」時，`17`、`16-17` 的片段被取回，而 `早上` 的片段被擋掉
    - 問母景點時，子景點的片段也會取回；用別名也能對到同一個景點
    - 沒有片段過門檻時，會退讓到母景點，並標記為退讓
    - 退讓後還是沒有，就回傳空結果
    - `space` 或 `time` 留空時，該維度不限制
    - `group_by` 照指定維度分組；`compose=contrast` 時各子查詢的結果分開
- **Seam 2：評估模組**。
  - 輸入題目檔和手寫的系統輸出（固定的取回集合、計畫、答案評分），驗證以下指標算得正確：集合的 recall、precision、F1，時間違規率，規劃器正確率，依題型和 dev／test 分組的彙總。
  - LLM 評審本身不測。
- **不寫自動測試的部分**：規劃器和生成器的 prompt 會呼叫 Opus，結果不固定，改成在 mock 的 dev 題目上實際跑評估來檢查。
- **Prior art**：repo 目前沒有任何測試，這次是第一批。`.venv` 已經裝了 `pytest`，就用它。

## Out of Scope

- 太陽換算（日出、日落、傍晚依經緯度和月份換成鐘點）和日曆換算（黃金週、盂蘭盆等假期）
- 移動經驗題型（起訖點、路線），以及任何需要座標或鄰近搜尋的功能
- 訓練或微調任何模型，包括 retriever 和 embedding
- 片段過多時的上限與合併摘要
- 反覆規劃（檢查證據後重新規劃）
- 景點階層的自動建構
- 真實 Reddit 資料的擴充、英文主實驗、公開釋出資料集
- 修改抽取流程或抽取 schema
- BM25 或其他 sparse 檢索
- 太陽、日曆、反覆規劃以外的延伸實驗：只有「LLM 直接輸出時間分布」和「few-shot 規劃器」在範圍內，當作可切換的設定

## Further Notes

- **論文定位**：
  - 主投 SIGSPATIAL，備案 CIKM。
  - 核心貢獻是週期性情境時間的表示與比對；檢索計畫和「景點階層退讓加揭露」是次要貢獻。
  - 要說清楚跟以下研究差在哪：Spatial-RAG（只有空間）、MRAG 和 TempRALM（線性時間、軟計分）、DeFuzzRAG（線性時間、硬過濾）、POI-QA（軌跡資料，不是旅客心得）。時段詞對應小時的做法引用 Shwartz 2022，不主張是自己的貢獻。
- **可行性的標準**（mock 的 test 題目上）：時間違規率明顯低於 dense retrieval，而且 recall 不低於硬過濾。
- **時空門檻要刻意設得寬鬆**：設太緊就等於硬過濾，論文「軟比對 vs 硬過濾」的主張會失去意義。
- **規劃、生成、評審都用 Claude Opus 5.5**：這是研究者的決定，論文裡要說明評審和生成用的是同一個模型。抽取維持現在的模型設定。
- **mock 擴充的分工**：agent 起草遊記、題目、`gold_plan`、`type`、`split`、景點階層檔，研究者審稿；`relevant_contents` 等抽取完成後，由研究者確認。
