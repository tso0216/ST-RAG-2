# 時空 RAG 主系統：旅客情境時間檢索

## Problem Statement

旅客想知道「某個景點在某個時間是什麼狀況」，例如「一月平日早上去晴空塔，看得到富士山嗎？要排多久？」。抽取流程已經把遊記拆成片段存進 DB，每個片段帶有景點、平日／假日、時段、月份。但現在沒有任何系統能用這些片段回答問題。

一般的 dense retrieval 只看語意，會把八月傍晚的經驗拿來回答一月早上的問題。直接拿現在的時間標籤做 metadata 過濾也不行：標籤格式太自由，同一個傍晚可能被標成 `17`、`16-17`、`晚上`，字面比對會漏掉；而且冷門景點的資料少，條件一嚴格就什麼都查不到。景點名稱也不一致：`晴空塔城` 和 `東京晴空塔城` 是同一個地方，天望甲板則屬於晴空塔，系統都無法辨認。

此外，研究者要把這套系統寫成國際論文，所以需要：

- 一組可以重現的評估
- 能跟現有研究比較的 baseline 和消融實驗

現有的時間 RAG 研究（TempRALM、MRAG、DeFuzzRAG）處理的都是線性的文件時間。旅客問的卻是每年、每週、每天都會重複的「情境時間」。

## Solution

做一套 RAG 主系統：

- 抽取時由 LLM 把片段的時間歸到固定的**時段**（早上、中午、下午、晚上、全天、不明），原文提到的具體鐘點留在片段內容裡。月份、平日／假日、時段三個維度在檢索時都是**硬過濾**，不做時間分布或平滑（見 `docs/adr/0001-hard-time-filter-with-backoff.md`）。
- 找不到相符的片段時，先做**時間退讓**（時段和月份各往外擴一格），再做**空間退讓**（往上退到外圍的行政區），取回的證據都要標記，回答時揭露跟問題的差距。
- 系統先由 LLM 產生一份**檢索計畫**，計畫由一到多個子查詢組成，每個子查詢指定地點、時間、想知道的面向；不限制的欄位留空。題型不寫死，新的題型只是欄位的新組合。
- 地點用 OpenStreetMap 解析（見 `docs/adr/0002-osm-place-resolution.md`）：
  - 抽取和規劃器寫出的地點都由 Nominatim 解析成 OSM 物件，同一個地方的不同寫法自然合併成同一個地點。
  - 景點的局部（展望台、樓層、境內的建築或小路）一律算在所在的景點裡，不另外成為地點。
  - 區域一律是行政區，問區域時納入範圍裡的所有地點。
- 附一套評估流程：擴充後的 mock 題目集，兩個 baseline，以及檢索、規劃、答案三方面的指標，用來驗證這個架構可不可行。

## User Stories

### 旅客（系統使用者）

1. As a 旅客, I want to 用口語問「某景點在某時間的狀況」, so that 我不用學任何查詢語法
2. As a 旅客, I want 系統只採用跟我問的時間相符的經驗, so that 我拿到的資訊適用於我要去的那個時段
3. As a 旅客, I want 系統在沒有相符的經驗時，用相鄰時段或相鄰月份的經驗回答並講明, so that 我知道這些資訊有多可靠
4. As a 旅客, I want 回答裡說明哪些內容來自不同旅客、不同天, so that 我不會把幾個人的經驗誤當成同一次
5. As a 旅客, I want 系統在完全沒有相關經驗時直接說沒有，並告訴我這個景點在哪些時段和月份有資料, so that 我不會被不相干時段的經驗誤導
6. As a 旅客, I want 問「什麼時候去人比較少」時，系統依時段整理各時段的狀況, so that 我能自己挑時間
7. As a 旅客, I want 問「傍晚在某區域哪裡適合看夕陽」時，系統依地點整理答案, so that 我能比較幾個候選地點
8. As a 旅客, I want 問「十二月傍晚跟晚上哪個比較不擠」時，系統分別找兩邊的證據再對照, so that 我拿到公平的比較
9. As a 旅客, I want 我說「晴空塔」時，系統也採用寫「天望甲板」「東京晴空塔」的經驗, so that 不會因為名稱不同而漏掉資訊
10. As a 旅客, I want 用「傍晚」「冬天」「週末」這種模糊說法提問, so that 我不用換算成精確的月份或時段
11. As a 旅客, I want 問題沒提到時間時，系統不限制時間, so that 所有相關經驗都會被考慮
12. As a 旅客, I want 時間寫得明確的經驗排在時間不明的經驗前面, so that 最可信的資訊先出現
13. As a 旅客, I want 跨年的條件（例如十二月到二月）正確處理, so that 冬天的問題不會漏掉一月和二月

### 研究者（論文作者）

14. As a 研究者, I want 用一個命令輸入問題就拿到答案、檢索計畫和取回的片段, so that 我能逐題檢查系統行為
15. As a 研究者, I want 時間標籤的比對規則（季節對應的月份、時段的相鄰關係）是固定、可重現的程式, so that 論文結果可以被重現
16. As a 研究者, I want 時段的鐘點邊界表明確寫出來，抽取和規劃共用同一張表, so that 論文能附上對照表，片段和問題的時段也一致
17. As a 研究者, I want 時間退讓和空間退讓可以各自關掉, so that 我能做「退讓」的消融
18. As a 研究者, I want 「不明」的折扣和語意門檻的 δ 都是可調參數, so that 我能做敏感度分析

20. As a 研究者, I want 規劃器只看計畫格式說明（zero-shot），不給範例和題型名稱, so that 我能主張系統有泛化性

22. As a 研究者, I want 每題有人工寫的 `gold_plan`，並另外量規劃器的正確率, so that 檢索變差時能分辨問題出在規劃還是檢索
23. As a 研究者, I want 用 dense retrieval 和不退讓的硬過濾當 baseline, so that 我能跟兩種常見做法比較
24. As a 研究者, I want 取回結果用集合的 recall、precision、F1 評估, so that 門檻式檢索取回的筆數不固定也能公平比較
25. As a 研究者, I want 量時間違規率（取回片段中，時間跟問題不相符、又沒有標成退讓或 `不明` 的比例）, so that 我能證明系統比 dense retrieval 少撈錯時段
26. As a 研究者, I want 由 LLM 評審逐條檢查答案是否涵蓋 `expect` 的重點, so that 我有答案品質的指標
27. As a 研究者, I want 量時間誤植率（答案把別的時段的經驗說成問題問的時段）, so that 我能證明揭露機制有效
28. As a 研究者, I want 題目分成 dev 和 test 兩組，門檻只在 dev 上決定, so that 不會在測試題上調參
29. As a 研究者, I want 依題型分組報告指標, so that 我能看出系統在哪類題目比較弱
30. As a 研究者, I want 一次跑完全部題目並輸出彙總結果, so that 我能快速比較各種設定和消融
31. As a 研究者, I want 抽取時 LLM 把原文的時間歸到時段，並在片段內容裡保留原文提到的具體時間, so that 檢索用一致的時段，回答時仍然講得出鐘點
32. As a 研究者, I want embedding 有快取, so that 重跑評估不會重複付費也不會變慢

34. As a 研究者, I want 能用「淺草」「押上」這類行政區提問, so that 「某區域附近」的問題也能對應
35. As a 研究者, I want 計畫裡的地點名稱解析不到 OSM 物件時，當作沒有這個地點, so that 不會把不相干的地點硬對上
36. As a 研究者, I want 改了抽取 prompt 之後，能用一個命令重新抽取整個 `main.db`, so that 所有片段的時段標籤都照同一套規則

## Implementation Decisions

### 名詞

- **片段**：DB `content` 表的一列，代表一則「某人在某時間到某地點」的經驗。
- **時間標籤**：片段或問題的 `month`、`day_type`、`time` 三個維度的值，格式跟抽取 schema 及 eval 的 `when` 相同。
- **時段**：`time` 維度的值，只能是早上、中午、下午、晚上、全天、不明其中一個。
- **檢索計畫**：由一到多個子查詢組成，外加 `group_by` 和 `compose`。
- **子查詢**：有 `space`、`time`、`aspect` 三個欄位，留空代表不限制。
- **時間退讓**：沒有證據時，時段和月份各往外擴一格再查。
- **景點**：旅客會拿來問的一個地方，例如寺社、塔、公園、商店街、店家。景點的局部不算獨立的景點。
- **區域**：一個行政區，例如淺草、押上、台東區。
- **地點**：景點或區域，對應到一個 OSM 物件。
- **空間退讓**：沒有證據時，往外圍的行政區找。
- **揭露**：回答時講明證據跟問題的差距（來自退讓、時間不明）。

### 時段的鐘點邊界

| 時段 | 鐘點 |
|---|---|
| 早上 | 5–10 點 |
| 中午 | 11–13 點 |
| 下午 | 14–17 點 |
| 晚上 | 18–4 點（含深夜、凌晨） |

- 這張表抽取和規劃共用。
- 片段的時段只能填一個：跨兩個時段的描述，挑佔比較多的那個；不分時段（例如「整天都很擠」）填 `全天`；看不出時間填 `不明`。
- 問題可以填一組時段：「傍晚」是下午加晚上，「10–12 點」是早上加中午。

### 模組

新開 `rag` 套件，跟 `extract` 並列。主要模組如下：

1. **時間標籤比對**（純函式、深模組）：輸入問題和片段的時間標籤，判斷相不相符、是不是靠時間退讓才相符。
   - 月份：問題可以是一組月份；單一月份、月份範圍（含 `12-2` 這種跨年範圍）、季節都換成月份集合。片段的月份也可以是範圍或季節，跟問題的集合有交集就算相符。
   - 季節定義：春 3–5、夏 6–8、秋 9–11、冬 12–2。
   - 時段：問題的一組時段裡包含片段的時段就算相符。片段是 `全天` 時，問任何時段都相符；問題填 `全天` 等於不限時段。
   - 平日／假日：字面相符。
   - 片段某個維度是 `不明`：該維度算相符，但這筆證據標成「時間不明」。
   - 相鄰關係（時間退讓用）：時段是環狀的，早上↔中午↔下午↔晚上↔早上；月份是環狀的，±1 個月；平日／假日沒有相鄰。
   - 不做太陽換算（日出、日落）和日曆換算（黃金週、盂蘭盆）。
2. **地點解析**（取代原本手建的景點階層，見 `docs/adr/0002-osm-place-resolution.md`）：
   - 輸入：日文名稱、城市、景點或區域。輸出：一個 OSM 物件（`osm_type` 加 `osm_id`），或「沒有這個地點」。抽取和規劃器共用這個模組。
   - 先查「名稱＋城市＋種類 → OSM 物件」的快取表，查不到才打 Nominatim：
     - 參數：`countrycodes=jp`、`accept-language=ja`，取第一筆，不做多個候選的消歧。
     - 景點用 `layer=poi`。
     - 區域用 `layer=address`，只接受行政區類型（例如 city、suburb、quarter、neighbourhood），所以不會對到車站或公車站。
   - 用公開的 nominatim.openstreetmap.org，限每秒 1 次請求、帶自訂 User-Agent。每次查詢的原始回應都存進 `main.db`，重跑時只讀快取，快取就是論文用的快照。
   - 解析得到的地點寫進 `place` 表；不同名稱解析到同一個 OSM 物件，就是同一個地點。
   - 景點存座標。區域除了座標，還存範圍（geojson）。
   - 每個地點記錄外圍的行政區：景點是包含它的最小行政區，區域是上一層行政區，從 Nominatim 的 `addressdetails` 取得。
   - 提供兩種查詢：
     - 某個區域範圍裡的所有地點：座標落在範圍裡的景點，加上代表點落在範圍裡的小區域。
     - 某個地點的外圍行政區。
   - 測試時，Nominatim 可以換成假的固定實作。
3. **Embedding**：
   - 用 OpenAI `text-embedding-3-large`，透過雲端 API 呼叫，API key 從環境變數 `OPENAI_API_KEY` 讀取。
   - 結果快取在 `main.db` 的新表，以文字和模型為鍵。
   - 對外介面是「文字列表進、向量列表出」，測試時可以換成假的實作。
4. **檢索**（主要的深模組）：輸入一份檢索計畫，輸出分好組的證據。
   - 每個子查詢的處理：
     - 解析 `space`：用地點解析模組對應到一個地點，解析不到就當作沒有這個地點，回傳空結果；留空就不限地點。
       - 景點：只取這個景點本身的片段，不取它所在區域的片段。
       - 區域：取這個區域本身的片段，加上範圍裡所有地點的片段。
     - 解析 `time`：三個維度都硬過濾；留空的維度不限。
     - 用 `aspect`（沒有就用原問題）的 embedding 算語意分數。
   - 分數 = 語意分數。片段有任何一個時間維度是 `不明` 時，再乘上一個小於 1 的折扣。
   - 門檻：語意分數不低於該子查詢的最高分減 δ。過門檻的全部取，不設上限、也不合併摘要。
   - 退讓，各只退一次，順序固定：
     1. 一筆都沒有時，做時間退讓：問題的時段和月份各往外擴一格（例如早上→早上＋中午＋晚上，十二月→十一到一月），同一個地點再查一次。
     2. 還是沒有，做空間退讓：`space` 退到外圍的行政區，照區域的規則取片段，時間用問題原本的條件。地點解析得到、但資料庫裡沒有它的片段時，也照常退讓。沒有外圍行政區就不退。
     3. 還是沒有，就回傳空結果，附上這個地點有資料的時段和月份，以及各有幾筆；區域則包含範圍裡的地點。
   - 時間退讓和空間退讓各自可以關掉，用來做消融。
   - 每筆證據附上片段內容、時間標籤、景點、來源文章、語意分數，以及三個標記：時間退讓、空間退讓、時間不明。
   - 依 `group_by`（`month`、`day_type`、`time_of_day`、`place`，可以多選）分組排序。`time_of_day` 直接照片段的時段分組，`全天` 和 `不明` 各成一組。`place` 照片段所屬的地點分組，組名用地點的繁中名稱；掛在區域本身的片段自成一組，不拆到底下的景點。`compose` 是 `contrast` 時，各子查詢的結果分開交給生成端。
5. **規劃器**：用 Claude Opus 5.5，一次產生檢索計畫，以 structured output 輸出。
   - prompt 只說明計畫格式（每個欄位的意思和可用的值，含時段的鐘點邊界表），不放範例，也不提題型名稱。
   - 地點的寫法跟抽取一樣：寫到景點層級，局部寫成所在的景點，局部名稱放進 `aspect`；另外寫出日文名稱、城市，並標明是景點還是區域。這段說明保持精簡。
   - 可以切換成 few-shot，當對照實驗。
   - 不做反覆規劃，那是延伸實驗。
   - oracle 模式：用 eval 的 `when` 取代規劃器解析出來的時間。
6. **生成器**：用 Claude Opus 5.5，依分好組的證據作答。
   - 標明出處：來自不同文章的證據要說明是不同旅客、不同天。
   - 依證據的三個標記揭露：來自時間退讓的，講明是哪個時段或月份的經驗；來自空間退讓的，講明是哪個地點的經驗；時間不明的，講明原文沒寫時間。
   - 沒有證據時，說沒有符合的經驗，並列出這個景點有資料的時段和月份。
7. **評估**：
   - 讀題目檔，跑系統，算出各項指標並依題型分組。
   - 檢索指標：取回集合對 `relevant_contents` 的 recall、precision、F1，時間違規率，以及有回答率（有取回證據的題目比例）。
   - 規劃器正確率：跟 `gold_plan` 比對欄位，例如該留空的有沒有留空、`group_by` 對不對。`space` 兩邊都先解析成 OSM 物件，再比對 OSM 物件和景點／區域的標記，不比對名稱字串。
   - 答案指標：由 Claude Opus 5.5 評審算 `expect` 覆蓋率和時間誤植率。
   - 支援 dev 和 test 分組，以及切換 baseline、消融、oracle 模式。
8. **Baselines**：
   - dense retrieval：只用語意分數取 top-k。
   - 硬過濾：跟系統一樣的時間比對和地點解析，但兩種退讓都關掉。

### 資料與 schema 變更

- 抽取 prompt 改成：
  - `time` 只能填早上、中午、下午、晚上、全天、不明，依上面的鐘點邊界表判斷。
  - `content` 要保留原文提到的具體時間（例如「早上 7 點左右幾乎沒有人」）。
  - `month`、`day_type` 的格式不變。
  - 地點寫到景點層級，局部寫成所在的景點，局部名稱留在 `content` 裡。除了繁中的 `poi_name`，另外輸出日文名稱、`city`，以及景點或區域。這段說明保持精簡。
  - 抽出的地點都用地點解析模組寫進 `place`。mock 抽取時解析失敗就報錯，列出失敗的名稱，不悄悄跳過。
- 改完後重新抽取 `main.db`。片段的 id 會變，題目檔的 `relevant_contents` 要重新對應。
- `main.db` 新增 embedding 快取表，以及 Nominatim 的查詢快取表（名稱＋城市＋種類 → OSM 物件，連同原始回應）。
- `place` 表改成一列一個 OSM 物件：`osm_type`、`osm_id`（兩欄一起當唯一識別）、`kind`（景點或區域）、`name_ja`（OSM 上的名稱）、`name_zh`（第一次抽到的繁中名稱，顯示用）、`city`、`lat`、`lon`；區域另存範圍，每個地點另存外圍行政區。
- `content` 表拿掉 `(poi_id, poi_name)` 的複合外鍵，只用 `poi_id` 指向 `place`；`poi_name` 改成保留抽取時寫的原始名稱。
- 刪除 `data/place_hierarchy.toml` 和手建階層的模組。
- 題目檔：
  - `when` 改成跟子查詢的 `time` 同一個格式。
  - 每題新增欄位：
    - `gold_plan`：人工寫的檢索計畫
    - `type`：停留、找時間、找地點、比較其中一種，只用於分組分析，系統不讀
    - `split`：`dev` 或 `test`
- 擴充後的 mock 照 mock README 的流程產生：約 10 個景點、30 題，其中 10 題 dev、20 題 test，每個景點都有負例。
- mock 階段維持繁中。真實 Reddit 資料和英文主實驗等可行性驗證通過後再做，不在這份 spec 範圍內。

### 檢索計畫的形狀

```
Plan:
  sub_queries: [SubQuery, ...]          # 一到多個
  group_by: [month | day_type | time_of_day | place]   # 可為空
  compose: merge | contrast
SubQuery:
  space: Space | null                   # null = 不限
  time:  {month?, day_type?, time?}     # 省略的維度 = 不限
         # month：一個或一組月份，可寫範圍（12-2）或季節
         # day_type：平日 | 假日
         # time：一個或一組時段（早上、中午、下午、晚上、全天）
  aspect: 想知道的面向 | null
Space:
  name: 繁中名稱
  name_ja: 日文名稱                      # 給 Nominatim 查詢
  city: 城市
  kind: 景點 | 區域
```

### 超參數

- 「不明」的折扣：先依常理定預設值，不在 test 題目上調。
- 語意門檻的 δ：在 dev 題目上決定。
- 論文另附敏感度分析。

## Testing Decisions

- **好的測試**只看外部行為：給定的輸入產生預期的輸出或排序，不檢查內部函式、中間值或實作細節。換掉內部實作時，測試不需要改。
- **Seam 1：檢索模組**，主要的測試點。
  - 輸入一份檢索計畫，輸出分好組的證據。
  - 測試時用記憶體內的 SQLite 塞入特定片段和地點，embedding 和 Nominatim 都換成假的固定實作，完全不打外部 API。
  - 時間標籤比對、計分、門檻、退讓、地點解析和區域包含都在這個 seam 後面，不另外對它們寫單元測試。
  - 應涵蓋的行為：
    - 問十二月時，只取回十二月的片段；`12-2`、`冬` 都能對上一月的片段
    - 問「下午、晚上」時，`下午`、`晚上`、`全天` 的片段被取回，`早上` 的片段被擋掉
    - 時間 `不明` 的片段會取回、標成時間不明，排在時間明確而且相符的片段之後
    - 問十二月早上沒有片段時，時間退讓取回十一月、一月，以及中午、晚上的片段，並標成時間退讓；時間退讓關掉時取不回來
    - 時間退讓後還是沒有，退到外圍行政區，並標成空間退讓；地點解析得到、但沒有任何片段時也會退
    - 兩種退讓後還是沒有，回傳空結果，附上這個地點有資料的時段和月份
    - 問區域時，區域本身、範圍裡的景點和小區域的片段都會取回；問景點時，不取回它所在區域本身的片段
    - 不同寫法解析到同一個 OSM 物件時，取回同樣的片段；解析不到時回傳空結果
    - `space` 或 `time` 留空時，該維度不限制
    - `group_by` 照指定維度分組；`compose=contrast` 時各子查詢的結果分開
- **Seam 2：評估模組**。
  - 輸入題目檔和手寫的系統輸出（固定的取回集合、計畫、答案評分），驗證以下指標算得正確：集合的 recall、precision、F1，時間違規率，有回答率，規劃器正確率，依題型和 dev／test 分組的彙總。
  - LLM 評審本身不測。
- **不寫自動測試的部分**：規劃器、生成器和抽取的 prompt 會呼叫 LLM，結果不固定，改成在 mock 的 dev 題目上實際跑評估來檢查。
- **Prior art**：`.venv` 已經裝了 `pytest`，測試放在 `tests/`。

## Out of Scope

- 時間分布、週期平滑和任何軟時間比對（見 `docs/adr/0001-hard-time-filter-with-backoff.md`）
- 太陽換算（日出、日落、傍晚依經緯度和月份換成鐘點）和日曆換算（黃金週、盂蘭盆等假期）
- 移動經驗題型（起訖點、路線），以及半徑或鄰近搜尋。座標只用來判斷地點是否在行政區範圍裡。
- Nominatim 多個候選的消歧（一律取第一筆，mock 的地點在起草時逐一確認）、自己架設 Nominatim
- 解析不到 OSM 物件的地點（真實資料才會遇到，先不處理）
- 訓練或微調任何模型，包括 retriever 和 embedding
- 片段過多時的上限與合併摘要
- 反覆規劃（檢查證據後重新規劃）
- 真實 Reddit 資料的擴充、英文主實驗、公開釋出資料集
- BM25 或其他 sparse 檢索
- 延伸實驗只有「few-shot 規劃器」在範圍內，當作可切換的設定

- **論文定位**：

  - 貢獻待定，等系統做完、看過實驗結果再決定。

  - 有回答率高於不退讓的硬過濾。
  - 時間誤植率夠低，證明揭露有效。
- **規劃、生成、評審都用 Claude Opus 5.5**：這是研究者的決定，論文裡要說明評審和生成用的是同一個模型。抽取維持現在的模型設定。
