# Spec：baseline 比較實驗

Status: ready-for-agent

## 問題

論文要證明時空 RAG 比一般做法好，但現在沒有任何可以跑的比較：

- 舊的評測程式（主系統 runner、Opus 評審、指標）已經刪掉，不還原，也不沿用它的設計。
- 對照組只有一個「對片段做 dense」的函式，放在檢索模組裡，沒有接上生成和評分。
- ptt_v2 題庫 50 題（停留經驗、移動經驗、找地點、找時間、比較各 10 題）已經有標準片段、`expect`、校準用的正反向答案，但沒有東西吃它。

## 解法

在 `src/strag_v3/eval/baseline/` 放一套自成一體的比較實驗：五個系統用同一份題目、同一個生成模型各跑一次，答案交給 JEV 評審，最後出一張系統 × 指標的比較表。評測相關的東西都在這個資料夾裡，不散在別處。

五個系統：

| 名稱 | 做法 | 用途 |
|---|---|---|
| `llm` | 不檢索，Opus 直接回答 | 證明常識補答不夠 |
| `dense_raw` | 對遊記原文切成的原文段做 dense，取 top-k | 一般的 RAG；不借用抽取的成果 |
| `dense_frag` | 對片段做 dense，取 top-k | 分開「抽取」和「結構化檢索」各自的貢獻 |
| `dense_filter` | LLM 從問題產生過濾條件，過濾片段後 dense 取 top-k | 最強的對照組 |
| `strag` | 完整的時空 RAG，預設參數 | 主系統 |

「原文段」指遊記原文切出來的一段文字，跟片段（抽取出來、帶地點和時間標籤的經驗）是兩回事。

## 使用者故事

1. 身為研究者，我要用一個指令讓指定的系統跑完 ptt_v2 全部 50 題並存檔，這樣每個系統的答案都留得住。
2. 身為研究者，我要五個系統用同一個生成模型，這樣差距只來自檢索。
3. 身為研究者，我要 `llm` 不看任何資料直接回答，這樣能看出模型只靠常識會答成什麼樣。
4. 身為研究者，我要 `dense_raw` 用跟其他系統相同的 248 篇遊記，這樣語料一致，標準文章都撈得到。
5. 身為研究者，我要 `dense_filter` 的地點只做字串比對、不展開區域、不退讓，這樣它跟主系統的差距正好是空間階層、相關判斷、退讓三樣。
6. 身為研究者，我要能指定 k，這樣主表之外還能出不同 k 的附表。
7. 身為研究者，我要 `strag` 照系統原本的設定跑（含它自己的相關判斷快取），這樣量到的是真正的主系統。
8. 身為研究者，我要每題記下答案、取回的片段、取回的文章、成本，這樣之後算指標不用重跑。
9. 身為研究者，我要某題出錯時只記那題的錯誤、其他題繼續跑，這樣一題失敗不會毀掉整批。
10. 身為研究者，我要評審和生成分成兩個指令，這樣改評審問法時不用重新生成答案。
11. 身為研究者，我要評審逐條判斷答案有沒有涵蓋 `expect`，這樣能算覆蓋率。
12. 身為研究者，我要評審對整份答案判一次「有沒有標準答案不支持的經驗說法」，這樣能看出系統有沒有亂補或錯置。
13. 身為研究者，我要來自「時間不明」片段的說法不算無支持，這樣主系統照設計撈時間不明的片段不會被罰。
14. 身為研究者，我要用 `--n` 讓評審對同一題重問幾次，這樣能看評審自己會不會前後不一。
15. 身為研究者，我要分數只用第 1 次的判斷，這樣 n 改變時分數的定義不變。
16. 身為研究者，我要評審結束時印出每一筆判斷不一致的地方和各次的 noul，這樣能逐筆檢查。
17. 身為研究者，我要看到一致率，覆蓋和無支持分開算，這樣能在論文裡交代評審的可信程度。
18. 身為研究者，我要評審每次執行都重新問、不讀快取，這樣每次都是獨立的一次量測。
19. 身為研究者，我要每次的結果檔和評審檔都另存、不覆寫，這樣不同次的數字可以互相比較。
20. 身為研究者，我要用現有的正反向答案校準評審，這樣正式跑之前就知道評審的問法靠不靠得住。
21. 身為研究者，我要校準同時驗覆蓋和無支持兩題，這樣兩個答案層指標都有依據。
22. 身為研究者，我要一張系統 × 指標的 markdown 表，這樣可以直接放進論文草稿。
23. 身為研究者，我要答案層兩項指標附 95% 信賴區間，這樣 50 題的結果不會被過度解讀。
24. 身為研究者，我要另一張依題型分的表，這樣能看出哪種題型差距最大。
25. 身為研究者，我要四個有檢索的系統都有文章級 recall，這樣原文段和片段兩種粒度可以放在同一欄比。
26. 身為研究者，我要三個以片段為單位的系統有 precision、recall、F1 和時間違規率，這樣能直接看到時間硬過濾的效果。
27. 身為研究者，我要失敗的題照樣算進分母，這樣系統的失敗不會被藏起來。
28. 身為研究者，我要報表列出出錯、地點解析不到、取回為空的題數，這樣知道低分是哪種原因。
29. 身為研究者，我要每個系統的成本，這樣能交代主系統多花了多少。
30. 身為接手的 agent，我要評測的程式、提示詞、結果都在同一個資料夾，這樣不用到處找。

## 實作決定

### 範圍與資料

- 題目只用 ptt_v2 的 50 題。舊的 `ptt/` 25 題標註規則不同，不用。
- 不調任何參數，所以不分 dev／test。
- 資料庫用 `data/ptt.db`，只讀；評測產物不寫進去（`strag` 自己的相關判斷快取和片段的 embedding 例外，那是系統原本的行為）。
- 唯一的退讓題（stay-10）照跑、照算。

### 模組

`eval/baseline/` 底下：命令列、讀題目、五個系統、評審、指標、提示詞、結果檔。

- 五個系統同一個介面：輸入一題，輸出答案、取回的片段 id、取回的文章 id、成本、錯誤訊息。`llm` 沒有取回；`dense_raw` 只有文章 id；`strag` 另外帶每個片段的退讓標記。
- 現有的片段 dense 函式搬進來當 `dense_frag`，原位置不留，相關的引用和測試跟著搬。
- JEV 的呼叫沿用現有的服務層（已有 Noul）。

### 生成

- 五個系統都用 `claude-opus-5-5`。
- `strag` 用系統原本的生成器提示詞（含退讓、時間不明的講明規則）。
- 三個 dense 系統共用一份精簡版：只根據證據回答、每個說法標出處、不同文章要講明是不同旅客。沒有退讓規則。
- `llm` 只給問題。
- 生成不快取，每次 `run` 都重新呼叫。

### 各系統的檢索

- `dense_raw`
  - 語料：資料庫裡有片段的 248 篇遊記，不多不少。目前本機只有 212 篇原文，缺的 36 篇用現有的 PTT 爬蟲補抓。
  - 切法：內文加推文，以段落為界，每段約 500 字，重疊 100 字。
  - 原文段和它的 embedding 存在 baseline 自己的 `chunks.db`，用 `build-chunks` 建一次。
  - k：主表 5，附表 3、10。
- `dense_frag`：原問題對所有片段的 cosine，取 top-k。k：主表 10，附表 5、20。
- `dense_filter`
  - Opus 從問題產生一組或多組過濾條件，每組是地點名、月份、平日／假日、時段；比較題可以多組。
  - 地點：對片段的地點名稱做字串比對，不經 Nominatim，不展開區域。
  - 時間：用跟主系統相同的比對規則，標成不明的維度算符合。
  - 沒有 JEV 相關判斷，沒有時間退讓和空間退讓。
  - 過濾後取 cosine top-k，多組各取 top-k 再合併。k 同 `dense_frag`。
- `strag`：規劃器 → 檢索（含兩種退讓）→ 生成器，全部預設參數。
- embedding 都用 `text-embedding-3-large`；embedding 結果固定，照存不重算。

### 評審

- 模型：`jev-1.14.0`，題型只用 Noul，noul ≥ 0.5 當「是」。
- 覆蓋：每條 `expect` 問一題。`state` 是問題、該條重點、答案全文。問「答案有沒有涵蓋這條重點」。
- 無支持：整份答案問一題。`state` 是問題、問的時間、標準片段全文和時間標籤、標註為「時間不明」的排除片段（註明不計分）、答案。問「答案裡有沒有標準答案不支持的經驗說法」；任何一條經驗說法對不上標準片段、也對不上時間不明片段，就是「有」。不再細分時空錯置和無據。
- `--n`（預設 1）：同一題用同一個模型重問 n 次。分數只用第 1 次；第 2 次以後只用來比對。
- 不一致：n 次的是／否不全相同就算不一致。`judge` 結束時每筆印一行（系統、題目 id、第幾條 `expect` 或無支持判斷、n 次的 noul），最後印一致率，覆蓋和無支持分開算；同樣的內容寫進評審檔。
- 評審不快取，每次 `judge` 都重新問。
- 沒有答案的題（出錯）不送評審：覆蓋率記 0，無支持記「沒有」。有答案文字的一律照常送評審，包括回答「沒有符合的經驗」的。

### 指標

| 指標 | 算法 | 適用 |
|---|---|---|
| `expect` 覆蓋率 | 每題是涵蓋條數除以總條數，再取各題平均 | 五個 |
| 無支持答案比例 | 判「有」的題數除以題數 | 五個 |
| 文章級 recall | 取回的文章裡是標準文章的數量，除以標準文章數；各題平均 | 四個有檢索的 |
| 片段級 precision、recall、F1 | 取回的片段對標準片段；各題平均 | `dense_frag`、`dense_filter`、`strag` |
| 時間違規率 | 違規片段數除以取回片段數，所有題合起來算 | 同上 |
| 成本 | 每題交給生成器的輸入 token 數、LLM 呼叫數、JEV 呼叫數（不含評審） | 五個 |

計分規則：

- 撈到標註為「時間不明」的排除片段，不算命中也不算誤撈，先從取回的片段裡拿掉。
- 時間違規：片段的時間標籤跟題目的時間條件矛盾。標籤是不明的不算矛盾；`strag` 標了退讓的片段不算；比較題只要符合任一選項的時間條件就不算。
- 出錯、地點解析不到、取回為空的題照樣算進分母（檢索指標記 0），報表另外列這三種的題數。
- 不量延遲。
- 信賴區間：答案層兩項附 95% 信賴區間，用逐題配對的 bootstrap，亂數種子固定。

### 命令列

| 指令 | 做什麼 |
|---|---|
| `build-chunks` | 讀 248 篇原文，切成原文段、算 embedding，寫進 `chunks.db` |
| `run --system <名稱> [--k N]` | 跑 50 題，存結果檔 |
| `judge <結果檔> [--n N]` | 評審，存評審檔，印不一致和一致率 |
| `report <評審檔…>` | 印比較表 |
| `calibrate [--n N]` | 用校準的正反向答案驗評審 |

### 檔案

- 結果檔：`runs/<時間>_<系統>_k<k>.json`，內容是每題的答案、取回的片段與文章、成本、錯誤，加上這次的設定。
- 評審檔：跟結果檔同名加 `.judge.json`，內容是 n 次的全部 noul、不一致清單、一致率。重跑 `judge` 另存一份帶時間的檔，不蓋掉舊的。
- 兩種檔都不覆寫。
- `chunks.db` 是可以重建的衍生資料，不進版控。

### 報表

- 主表：列是系統，欄是指標；不適用的格子留空。
- 第二張表依題型分，只列平均，不附信賴區間。
- 都是 markdown。

### 校準

- 用 ptt_v2 現有的校準檔（每題一個反向答案）和照 `expect_sources` 拼出來的正向答案；正向答案的拼法沿用出題工具現有的規則。
- 覆蓋：正向答案每條都要判涵蓋，反向答案每條都要判不涵蓋。
- 無支持：正向答案要判「沒有」，反向答案要判「有」。
- 印出沒過的條目。
- 出題工具裡壞掉的 `calibrate`（依賴已刪的舊評審）拿掉。

### 清理

- 舊評測留下來、已經跑不了的測試一併刪掉。
- 更新系統 README 裡 `eval/` 的說明，並修正過期的資料量（現在是 248 篇、648 個片段）。

## 測試決定

好的測試只看外部行為：給輸入、看輸出，不檢查內部怎麼做。全部不打網路。

要測的：

- 指標計算：給題目、系統輸出、評審判斷，檢查各項指標；特別是時間不明片段不計分、退讓片段不算違規、比較題的時間條件、失敗題算進分母。
- 評審：用假的 TypeSafe client。檢查每條 `expect` 各問一題、無支持問一題、`--n` 重問 n 次、分數只取第 1 次、不一致清單和一致率、沒有答案的題不送評審。
- `dense_filter` 的過濾邏輯：地點字串比對、時間比對（不明算符合）、多組合併。
- 原文段的切法：段落邊界、長度、重疊、內文加推文。

不測的：五個系統的端到端。

參考現有的寫法：相關判斷的測試（假 TypeSafe client 的用法）、片段 dense 的測試、假 Nominatim。現有的假 TypeSafe client 是照相關判斷的 `state` 寫的，評審的 `state` 不同，需要能指定回傳值的版本。

## 不做的事

- 揭露／拒答正確率，以及為它補出的退讓題、沒資料題。
- 消融實驗（關時間硬過濾、關空間階層、換相關判斷、關退讓、用標準計畫取代規劃器）。
- 把答案拆成一條條說法逐條判斷；時空錯置和無據分開算。
- 多個評審模型取眾數。
- 「k 等於標準片段數」那組。
- 生成或評審跑多次取平均。
- 抽取正確率的人工驗證、沒經過 `plan` 篩選的自然問法題組。
- 改 `data/ptt.db` 的內容、改主系統的檢索或生成。
- 寫 ADR、改 GLOSSARY。

## 補充

實作順序，各開一張 ticket：

1. 骨架、讀題目、評審（兩題 Noul、`--n`、不一致清單）、`calibrate`。
2. 指標與 `report`，接上 `strag` 和 `dense_frag`（不需要新資料）。
3. `llm`、`dense_filter`（需要新提示詞）。
4. 補抓 36 篇原文、`build-chunks`、`dense_raw`。

評審先做、先校準，之後每接一個系統就有數字可看；補抓原文放最後，不擋前面。

已知風險：

- 無支持判斷是二分的，一句對不上就算「有」。`llm` 可能接近 100%，`strag` 撈到標註判「無關」的片段也會中，50 題的鑑別力可能不夠。跑完若五個系統擠在一起，再回頭改問法。
- `jev-1.14.0` 之前公告過會停用。評審不快取，停用後舊的判斷只留在評審檔裡，沒辦法重問。
- 無支持那題的 `state` 要放整份答案加上所有標準片段，長度可能很長；第 1 張 ticket 要先確認 JEV 吃得下。
- 評審的呼叫量：五個系統跑一次 `judge` 約 1,400 次，`--n 3` 約 4,000 次（50 題 × 平均 5.5 題判斷 × n × 5 個系統）。
