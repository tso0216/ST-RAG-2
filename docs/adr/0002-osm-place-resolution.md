# 取消手建景點階層，改用 OpenStreetMap 解析地點

原本的設計用一份手建的階層檔處理地點：每個節點記錄正式名稱、別名和母節點，名稱靠字串比對別名，空間退讓是往上退到母節點。我們改成：抽取和規劃器都把地點寫到景點層級（景點的局部算在所在的景點裡），並寫出日文名稱、城市和種類（景點或區域），再由 Nominatim 解析成 OSM 物件。同一個 OSM 物件就是同一個地點。區域一律是行政區，問區域時用座標判斷哪些地點在範圍裡。空間退讓改成退到外圍的行政區。

理由：

- 手建別名表只能涵蓋人想得到的寫法，資料一多就維護不了；OSM 物件是外部的穩定身分，不同寫法會自然合併。
- 「景點包含景點」（天望甲板屬於晴空塔）在 OSM 裡大多沒有資料。在 prompt 裡要求把局部寫成所在的景點，就不需要這種包含關係。LLM 懂這個常識，但不知道 OSM 實際用哪種寫法，所以 LLM 只負責決定是哪個景點，名稱由 Nominatim 去對。
- 改用行政區的範圍和外圍關係，不必人工劃分區域，空間退讓的語意也還是「往上退一層」。

## Considered Options

- **只用 Nominatim 地址各層的字串當區域，不存座標**：區域之間的包含和區域名稱都得靠字串比對，又回到別名比對的老問題。
- **保留精簡的人工母子檔，只把節點換成 osm_id**：還是要人工維護，而且局部併進景點之後，母子關係只剩下區域，交給 OSM 就夠了。
- **空間退讓改成半徑搜尋**：多一個距離參數要調，揭露時也比「退到外圍的行政區」難講清楚。

## Consequences

- spec 原本的 Out of Scope 寫「不需要座標」，這條拿掉；但仍然不做半徑或鄰近搜尋。
- 解析結果會隨 OSM 更新而變，所以 Nominatim 的原始回應要存成快照，重跑時只讀快照。
- Nominatim 一律取第一筆，對錯不會自動發現。mock 只用起草時逐一確認過的地點；OSM 沒有資料的區域（例如嵐山）不能用。
- 真實資料一定會有解析不到的名稱，怎麼處理留到真實資料的階段再決定。
